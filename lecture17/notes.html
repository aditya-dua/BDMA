Section 1: Why a Second Database — Polyglot Persistence

By the end of Lecture 16 you had a working analytics product: 15,000 ride bookings in MongoDB Atlas, an aggregation pipeline that computes revenue by vehicle type and failure rate by hour, and an Atlas Charts dashboard that renders the result. It is genuinely good work. It is also, for a specific class of question, the wrong machine.

Open that dashboard and every tile fires an aggregation pipeline. The pipeline scans, groups, sorts and returns. On 15,000 documents that is comfortably fast. On 15,000,000 — the volume a real ride-hailing firm generates in a few weeks — the same pipeline becomes a multi-second operation, and you are running it again for every analyst who refreshes the page.

Polyglot persistence is the practice of running more than one database, each chosen for the job it is best at. You met the term in Lecture 11 as a myth-buster. In Module 4 it becomes an architecture: MongoDB is the system of record — the durable, queryable, auditable truth — and Redis is the speed layer — a small, volatile, extremely fast set of pre-computed answers.

The Latency Budget

The argument for a speed layer is not aesthetic. It is arithmetic. These are the numbers every systems architect carries in their head:

OperationTypical LatencyRelative CostWhat It Means
Read from RAM~100 nanoseconds1×Effectively instant — the CPU barely waits
Read from SSD~100 microseconds~1,000×Fast, but a thousand RAM reads could have happened
Database round trip over a network~1–10 milliseconds~10,000–100,000×Query planning, disk access, serialisation, network
Human perception of "instant"~100 milliseconds—Your entire page-load budget

Read the last two rows together. If a dashboard page needs twelve metrics and each costs a 10 ms aggregation, you have spent 120 ms before a single pixel is drawn — you have blown the budget on data alone. If each metric is a single in-memory lookup at well under a millisecond, twelve of them cost less than one MongoDB query.

The business translation: Amazon's often-quoted internal finding was that every additional 100 ms of latency cost roughly 1% in sales. You do not need to believe the precise figure to accept the direction. Latency is not an engineering vanity metric — it is conversion, analyst productivity, and the difference between a dashboard people check hourly and one they stopped opening.

Division of Labour

🗄️ MongoDB — System of Record

Holds all 15,000 booking documents, permanently and durably. Answers any question you think of later, including ones nobody anticipated.

Optimised for: completeness, flexibility, durability. Costs: milliseconds per query, and the query cost grows with the data.

⚡ Redis — Speed Layer

Holds a few dozen pre-computed aggregates: total bookings, revenue by vehicle, top pickup points, today's unique customers.

Optimised for: read latency. Costs: you must decide in advance what to track, and losing it is survivable because it can be rebuilt from Mongo.

The safety property that makes this architecture sane: everything in Redis is derived. If the Redis process dies and the memory is lost, you have lost nothing that cannot be recomputed by replaying the rides collection. That is precisely why a volatile store is an acceptable component — and precisely why it must never be the only copy of anything.

Section 2: What Redis Actually Is

Redis stands for REmote DIctionary Server. Salvatore Sanfilippo released it in 2009 after an analytics workload at his own startup proved too slow on MySQL — a lineage worth noting, because analytics is exactly what we are about to use it for.

Three design decisions define it.

1. It Lives in RAM

The entire dataset is held in main memory. There is no buffer pool, no cache-miss path, no "is this page on disk?" branch. Every read is a memory read. The consequence is both halves of the trade: single-digit-microsecond operations, and a hard ceiling at the size of your RAM.

2. It Is Single-Threaded — Deliberately

Command execution runs on one thread. Students usually hear this as a defect. It is the opposite.

A multi-threaded in-memory store must protect every shared structure with locks. Lock acquisition, contention, and the cache-line traffic that comes with it routinely cost more than the operation being protected. Redis removes the problem by removing concurrency: commands are executed one at a time, in arrival order, to completion.

The payoff is free atomicity. INCR is not "read, add one, write" with a race in the middle — it is one indivisible step. No application-level locking, no lost-update bug, no compare-and-swap retry loop. Two hundred concurrent booking events can increment the same counter and the count will be exactly right.

Modern Redis does use additional threads for I/O and for background persistence, but the command-execution model remains serial, and that is the property you reason about.

3. The Values Are Data Structures — This Is the Whole Point

This is the distinction that separates Redis from a plain cache such as Memcached, and the one most worth carrying out of this lecture.

Memcached (plain cache)Redis (data-structure server)
Value modelAn opaque blob of bytesA typed structure the server understands
To add 1 to a counterFetch the blob, parse it, add, serialise, write back — and race with every other clientINCR key — one atomic server-side operation
To keep a top-10 listFetch everything, sort in the application, write backZINCRBY then ZREVRANGE key 0 9 — the server maintains the order
Network costThe whole value crosses the wire on every changeOnly the delta crosses the wire

Say this precisely: Redis is a key-value store in which the value is a rich data structure manipulated in place on the server. That one sentence explains why a "cache" can serve as the engine of the live dashboard you will build next week.

Section 3: The Five Core Data Structures

Every example below uses the course dataset — the bdma.rides collection of 15,000 Delhi-NCR Uber-style bookings from calendar 2024.

String — The Counter and the Cache Slot

A String holds text, a number, or serialised JSON, up to 512 MB. When the content is numeric, Redis can do arithmetic on it atomically.

# A plain value
SET    rides:last_loaded "2024-12-31T23:59:59Z"
GET    rides:last_loaded

# A counter — atomic, no read-modify-write race
INCR   rides:2024-03-14:total           # -> 1, then 2, then 3 ...
INCRBY rides:2024-03-14:completed 1
INCRBYFLOAT revenue:2024-03-14 412.50   # booking_value is a decimal

# A cached JSON payload with a 60-second life
SETEX dash:summary:cache 60 '{"total":15000,"completed":9343}'
Business useWhy a String
Bookings today, completions today, cancellations todayINCR is atomic and O(1) regardless of how many writers there are
Running revenue for a dateINCRBYFLOAT accumulates booking_value without re-reading the total
Feature flags (flag:surge_pricing = on)Read on every request; one memory lookup instead of a config query
Cached JSON for an expensive reportSETEX gives automatic invalidation — the cache cannot go stale past its TTL

Hash — An Object Under One Key

A Hash maps field names to values inside a single key. It is the natural home for a record with several attributes that you want to update independently.

# One booking's live state
HSET  booking:CNR3000142 status "Completed" vehicle_type "Go Sedan" \
      pickup "Connaught Place" booking_value 412.5
HGET  booking:CNR3000142 status            # -> "Completed"
HGETALL booking:CNR3000142                  # -> every field and value

# Payment-method mix, as one object rather than five keys
HINCRBY dash:payment "UPI" 1
HINCRBY dash:payment "Cash" 1
HGETALL dash:payment
# -> UPI 6755, Cash 3797, Uber Wallet 1769, Credit Card 1619, Debit Card 1062

Why a Hash rather than five Strings? One key instead of five means one round trip to read the whole group (HGETALL), one key to expire, and markedly lower memory overhead — Redis stores small hashes in a compact encoding. Use a Hash whenever the fields are read together and belong to the same conceptual object.

List — Ordered, with Fast Ends

A List is a linked list of strings. Pushing and popping at either end is O(1); reading the middle is not. That shape makes it a queue or a recent-activity feed, not a general-purpose array.

LPUSH  feed:recent_bookings "CNR3000142 · Go Sedan · Connaught Place → Aerocity"
LPUSH  feed:recent_bookings "CNR3000143 · Auto · Noida Sector 62 → Sector 18"
LRANGE feed:recent_bookings 0 9      # the ten most recent
LTRIM  feed:recent_bookings 0 99     # keep only the latest 100 — bounded memory

# As a work queue
LPUSH  queue:driver_payouts "CNR3000142"
RPOP   queue:driver_payouts          # a worker takes the oldest item

The pattern worth memorising: LPUSH followed by LTRIM gives you a feed that can never grow without limit. A recent-activity strip on a dashboard should always be capped this way.

Set — Unique Membership

An unordered collection with no duplicates. Adding a member that already exists is a no-op, which makes uniqueness free rather than something you check for.

SADD    customers:2024-03-14 "CID482910"
SADD    customers:2024-03-14 "CID482910"   # -> 0, already present
SCARD   customers:2024-03-14               # unique customers that day
SISMEMBER customers:2024-03-14 "CID482910" # O(1) membership test

SADD    vehicles:used:2024-03-14 "Go Sedan" "Auto" "eBike"
SMEMBERS vehicles:used:2024-03-14

The genuinely valuable part is set algebra, executed inside the server:

# Customers who booked on BOTH days — day-over-day retention
SINTER customers:2024-03-13 customers:2024-03-14

# Everyone who booked on either day
SUNION customers:2024-03-13 customers:2024-03-14

# Churn candidates: booked on the 13th, did not return on the 14th
SDIFF  customers:2024-03-13 customers:2024-03-14

The cost to watch: a Set stores every member in full. One million customer IDs of the form CID482910 is roughly 60–80 MB per day, per key. That is fine for a day or two and ruinous for a year. Section 4 shows what to use instead when you only need the count.

Sorted Set (ZSET) — The One with No SQL Equivalent

A Sorted Set is a Set in which every member also carries a numeric score, and the server permanently maintains the members in score order. Insertion, score update, and rank lookup are all O(log N).

# Accumulate revenue per vehicle type as bookings arrive
ZINCRBY dash:vehicle:revenue 412.50 "Go Sedan"
ZINCRBY dash:vehicle:revenue 688.00 "Premier Sedan"

# Top three revenue earners, with their totals — instantly
ZREVRANGE dash:vehicle:revenue 0 2 WITHSCORES
# 1) "Premier Sedan"  2) "536855"
# 3) "Go Sedan"       4) "491473"
# 5) "Uber XL"        6) "431927"

# Busiest pickup points
ZINCRBY   dash:pickup:top 1 "Noida Sector 62"
ZREVRANGE dash:pickup:top 0 4 WITHSCORES
# Noida Sector 62 1209 · IGI Airport 1183 · New Delhi Railway Station 1179
# Gurgaon Cyber City 1178 · Connaught Place 1139

ZRANK   dash:pickup:top "Connaught Place"   # ascending rank
ZSCORE  dash:pickup:top "IGI Airport"       # -> 1183
ZRANGEBYSCORE dash:vehicle:revenue 400000 +inf

Why this one matters most. "Give me the top 10 by revenue" in SQL or a MongoDB pipeline means sorting the aggregate at query time — work proportional to the number of groups, repeated on every read. In a ZSET the ordering is maintained incrementally on write, so the read is a slice of an already-sorted structure. Leaderboards, trending lists, top-N by any accumulating measure, and rank-of-one-item queries are the cases where Redis is not merely faster but structurally better suited.

The trap inside every leaderboard. A ZSET ranks by whatever score you put in it and has no idea whether that score deserves to be trusted. Rank the 24 hours of our dataset by failure rate and 03:00 comes top at 43.48% — on 46 bookings for the whole year. That is a small-sample artifact, not a signal, and acting on it sends an operations team to investigate an hour that barely exists. The worst failure rate among the hours that actually carry volume is 17:00 at 39.92% — higher than the 18:00 peak's 37.14%, even though 18:00 takes 1,373 bookings to 17:00's 1,062.

The rule: never rank by a ratio without gating on its denominator. In MongoDB that gate is one stage — { $match: { bookings: { $gte: 1000 } } } after the $group. In Redis there is no such stage, so you must keep the denominator in a second structure and filter in application code before you display. Same discipline, and it is now your job rather than the query engine's.

Section 4: Counting at Scale — Bitmaps and HyperLogLog

This section is the hinge of Module 4. Everything you build in Lecture 18 rests on it.

Bitmaps — One Bit per User

A Bitmap is not a separate type. It is a String addressed one bit at a time. SETBIT key offset 1 turns on the bit at a given position, growing the underlying string as needed.

Map each customer to a stable numeric offset. Our IDs make this trivial: CID482910 → offset 482910.

# Customer CID482910 was active on 14 March
SETBIT dash:customers:2024-03-14 482910 1

# Was a specific customer active?
GETBIT dash:customers:2024-03-14 482910    # -> 1

# How many distinct customers were active that day?
BITCOUNT dash:customers:2024-03-14         # exact, server-side popcount

The Memory Arithmetic — Do This on the Board

One bit per user. One million users is 1,000,000 bits.

1,000,000 ÷ 8 = 125,000 bytes ≈ 125 KB.

Tracking whether each of a million customers was active today costs about as much memory as a single photograph. A year of daily keys — 365 of them — is roughly 45 MB. For ten million users it is 1.25 MB per day and about 456 MB per year. These are numbers you can put in a budget.

Compare that with the Set from Section 3. The same one million customers stored as full CID… strings is of the order of 60–80 MB per day — several hundred times larger. The bitmap wins because it stores a yes/no fact about a known population rather than the identifiers themselves.

BITOP — Retention in Two Commands

# Customers active on BOTH 13 and 14 March
BITOP AND dash:retained:0313-0314 dash:customers:2024-03-13 dash:customers:2024-03-14
BITCOUNT  dash:retained:0313-0314       # -> day-over-day returning customers

# Active on EITHER day (reach)
BITOP OR  dash:reach:0313-0314 dash:customers:2024-03-13 dash:customers:2024-03-14
BITCOUNT  dash:reach:0313-0314

# Churned: active on the 13th but not the 14th
BITOP NOT dash:inactive:0314 dash:customers:2024-03-14
BITOP AND dash:churn:0313    dash:customers:2024-03-13 dash:inactive:0314
BITCOUNT  dash:churn:0313

Why this is remarkable: BITOP AND across a million users is a bitwise AND over 125 KB of memory — the CPU processes 64 users per machine word. A retention cohort that would be a $lookup-and-$group pipeline over millions of documents in MongoDB becomes two commands and sub-millisecond work here. This is the single idea the Lecture 18 dashboard is built on.

The precondition, stated honestly: bitmaps require a dense, stable integer identity per user. CID482910 gives us one for free. Real systems with UUID keys must maintain a separate ID → offset mapping (often a Redis Hash plus an INCR counter). And the bitmap's size is set by the largest offset used, so sparse, very large IDs waste memory. Never hash a UUID into an offset — collisions silently corrupt the count.

HyperLogLog — Approximate Cardinality in Fixed Memory

When you cannot assign offsets, or the population is unbounded, HyperLogLog counts distinct items in a fixed 12 KB, regardless of whether you feed it a thousand items or a billion.

PFADD   dash:hll:customers:2024-03-14 "CID482910" "CID100233" "CID775012"
PFCOUNT dash:hll:customers:2024-03-14        # approximate distinct count

# Weekly uniques — merge seven daily keys, no double counting
PFMERGE dash:hll:week:11 dash:hll:customers:2024-03-11 dash:hll:customers:2024-03-12 \
        dash:hll:customers:2024-03-13 dash:hll:customers:2024-03-14
PFCOUNT dash:hll:week:11
SetBitmapHyperLogLog
Memory for 1M users~60–80 MB~125 KB12 KB (fixed, always)
AccuracyExactExact~0.81% standard error
Can list members?YesYes, by scanning bitsNo — never
Needs integer IDs?NoYesNo
Combine keysSINTER, SUNION, SDIFFBITOP AND/OR/XOR/NOTPFMERGE (union only)
Use whenYou need the actual membersDense integer IDs; you need intersectionsHuge or unbounded keyspace; a 1% error is immaterial

The trade, in business language: HyperLogLog reports 1,000,000 unique visitors when the truth is somewhere around 991,900 to 1,008,100. For a traffic chart in a board pack, that is indistinguishable from exact. For "how many customers do we bill this month", it is unusable. Approximation is a decision about the question, not about the technology — and you should make it explicitly, in front of the person who consumes the number.

Section 5: Key Naming, Expiry and Eviction

The Key Naming Convention IS the Schema

Redis has no tables, no columns, and no catalogue. Nothing stops you creating x1, temp, and revenue_final_v2_USE_THIS side by side. Six months later nobody — including you — knows what is in the database.

The universal convention is a colon-delimited hierarchy, read left to right from broadest to narrowest:

<namespace>:<entity>:<identifier>:<attribute>

rides:2024-03-14:completed          # String  — completed bookings on a date
dash:actives:2024-03-14             # Bitmap  — daily-active customer flags
dash:vehicle:revenue                # ZSET    — revenue by vehicle type
dash:payment                        # Hash    — booking count per payment method
booking:CNR3000142                  # Hash    — one booking's live state
session:CID482910                   # Hash    — a customer's app session

Four rules worth enforcing in code review:

1. Pick one separator — : — and never mix in _ or - at the hierarchy level. 2. Put the date in ISO form (2024-03-14) so keys sort lexicographically into chronological order. 3. Make the prefix identify the owning feature (dash:), so one team's keys can be found, expired, or migrated without touching another's. 4. Write the key schema down in a table — it is documentation nobody can derive from the server.

Never run KEYS * on a production server. It is O(N) over the entire keyspace, and because Redis is single-threaded it blocks every other client until it finishes. On a few million keys that is seconds of a total outage, caused by someone looking around. Use SCAN, which returns a cursor and a small batch, letting other commands interleave:

# Wrong — blocks the whole server
KEYS dash:*

# Right — incremental, non-blocking
SCAN 0 MATCH dash:customers:* COUNT 100
# -> returns a new cursor plus up to ~100 keys; repeat until the cursor is 0

Expiry — Memory That Cleans Itself

EXPIRE dash:customers:2024-03-14 7776000   # keep 90 days (in seconds)
TTL    dash:customers:2024-03-14           # -> seconds remaining
TTL    dash:vehicle:revenue                # -> -1, no expiry set
TTL    missing:key                         # -> -2, key does not exist
PERSIST dash:customers:2024-03-14          # remove the expiry
SETEX  dash:summary:cache 60 "{...}"       # set value and TTL in one step

Expiry is how a speed layer stays small. Daily keys that nobody will query after a quarter should carry a 90-day TTL from the moment they are created — set it in the same transaction as the first write, not in a cleanup job you will forget to run.

Eviction — What Happens When RAM Runs Out

Suppose memory fills anyway. Redis's behaviour is governed by maxmemory and maxmemory-policy:

PolicyBehaviour When FullRight For
noevictionWrites fail with an error; reads keep workingThe default. Correct when every key matters and silent data loss is unacceptable
allkeys-lruEvicts the least recently used key, whether or not it has a TTLA pure cache where anything can be rebuilt from the source of truth
volatile-lruEvicts the least recently used key among those with a TTL; keys without one are protectedMixed workloads — the pattern our dashboard uses
allkeys-lfuEvicts the least frequently used keyCaches with a stable hot set and occasional one-off scans
volatile-ttlEvicts the key with the nearest expiry firstShort-lived session or token stores
 
CONFIG SET maxmemory 512mb
CONFIG SET maxmemory-policy volatile-lru
INFO memory          # used_memory_human, maxmemory_policy, evicted_keys

Why a cache needs an eviction policy at all: a cache without one is not a cache — it is an unbounded memory leak that eventually takes the process down. The policy is the explicit statement of which data you are willing to lose first. Choosing it is a business decision disguised as a config line: volatile-lru says "my dashboard aggregates are protected; my cached report payloads are expendable."

Section 6: Persistence — and When Redis Is the Wrong Answer

RDB Snapshots vs AOF

Redis is in-memory, not memory-only. It offers two ways to put data on disk, and they trade durability against write cost in opposite directions.

RDB — SnapshotAOF — Append-Only File
MechanismForks a child process that writes a point-in-time binary dump of the whole datasetAppends every write command to a log, which is replayed on restart
Worst-case lossEverything since the last snapshot — minutesAbout one second with appendfsync everysec; near-zero with always
Write-path costNear zero between snapshots; a CPU and memory spike during the forkContinuous, modest; always makes every write wait on fsync
Restart speedFast — load a compact binary fileSlower — replay the log (mitigated by periodic rewrites)
File sizeCompactLarger; needs background rewriting to stay bounded
 
# Snapshot if 1 change in 900s, 10 in 300s, or 10,000 in 60s
CONFIG SET save "900 1 300 10 60 10000"

# Enable the append-only log, flushed once per second
CONFIG SET appendonly yes
CONFIG SET appendfsync everysec

BGSAVE       # take a snapshot now, in the background
LASTSAVE     # Unix timestamp of the last successful snapshot

The sentence to remember: Redis can lose the last few seconds of writes. For a speed layer that is irrelevant — the aggregates are derived and can be rebuilt by replaying bdma.rides. For a payment ledger it is disqualifying. The same property is acceptable or fatal depending entirely on what the data is. That judgement, not the config syntax, is what an MBA is paid for.

Three Cases Where Redis Is the Wrong Answer

❌ Primary store for data you cannot lose

Bookings, payments, contracts, audit trails. Even with AOF always, you are paying a durability premium on a system designed for the opposite trade. Use PostgreSQL or MongoDB.

❌ Datasets larger than RAM

Redis is priced per gigabyte of memory, which costs roughly an order of magnitude more than SSD. A 2 TB dataset in Redis is an architectural error with an invoice attached.

❌ Complex ad-hoc queries

There is no "WHERE booking_value > 500 AND vehicle_type = 'Auto'" unless you built that index yourself. Exploratory analysis belongs in the system of record.

The decision rule: use Redis when the access pattern is known in advance, the read volume is high, the latency budget is tight, and the data is derived or reconstructible. Fail any one of those and you want a different store — most often the one you already have.

Key Takeaways

✓ What You Should Be Able to Say After This Session

  1. Polyglot persistence is an architecture, not a slogan. MongoDB is the system of record; Redis is the speed layer holding derived answers. Because Redis data is derived, losing it is survivable — which is what makes a volatile store acceptable in production.
  2. The case for a speed layer is arithmetic. RAM ~100 ns, SSD ~100 µs, a network database round trip ~1–10 ms. A twelve-tile dashboard cannot afford twelve aggregations inside a 100 ms budget.
  3. Single-threaded is a feature. No locks, no contention, and every command is atomic — so concurrent writers can increment the same counter and still be exactly right.
  4. The values are data structures, and that is the whole point. Strings for counters, Hashes for objects, Lists for feeds, Sets for uniqueness and set algebra, Sorted Sets for ranked top-N — the last of which SQL cannot replicate cheaply.
  5. One bit per user changes what is affordable. 1,000,000 bits ÷ 8 = 125 KB for a day of active flags; BITOP AND plus BITCOUNT turns a retention cohort into two commands. HyperLogLog trades exactness and member listing for a fixed 12 KB at ~0.81% error.
  6. No schema means the key naming convention IS the schema. Colon-delimited namespaces, ISO dates, TTLs set at write time, an explicit maxmemory-policy — and SCAN, never KEYS *, on anything that matters.
