Indexing & the Aggregation Framework

Making queries fast — then turning 15,000 raw bookings into the handful of numbers a management meeting actually needs.

Two halves, one collection

Half 1 · Indexing (~40 min)

Why an unindexed query is O(n), how a B-tree fixes it, the ESR rule for compound indexes, and how to read explain() — plus why more indexes is not better.

Half 2 · Aggregation (~40 min)

Pipelines as a conveyor belt of stages. Seven real business questions answered against bdma.rides, and the output materialised for Lecture 15's dashboard.

The through-line: indexing makes retrieval fast; aggregation turns retrieval into an answer. A dashboard needs both.
The Problem & The Fix

A scan reads everything. A B-tree does not.

With no usable index, db.rides.find({ "route.pickup": "Connaught Place" }) reads all 15,000 documents to return ~1,139. Plan stage: COLLSCAN — and it is O(n), with no early exit.

Collection sizeDocs read per queryResponseBusiness reality
15,000 (today)15,000~30 msFeels instant — the problem is invisible
1,500,0001,500,000~3 sA dashboard tile that visibly stalls
15,000,00015,000,000~30 sTimeouts. The report is abandoned, not slow.

COLLSCAN — O(n)

Read the whole book to find one sentence. Twice the data, twice the work — and every document dragged through RAM evicts useful data from cache, slowing unrelated queries too.

IXSCAN — O(log n)

A sorted B-tree of values plus pointers: read the index page, turn to page 412, read one sentence. Finding one doc among 15 million costs about twice as much as among 15 thousand — not a thousand times.

Translation: a 400 ms query becomes ~12 s at 30× the data. That is not degradation — it is the difference between a report people open every morning and one they stop opening.
Syntax

createIndex() — and when direction matters

db.rides.createIndex({ status: 1 })                 // 1 = ascending
db.rides.createIndex({ booking_value: -1 })         // -1 = descending
db.rides.createIndex({ "route.pickup": 1 }, { name: "pickup_idx" })

db.rides.getIndexes()
db.rides.dropIndex("pickup_idx")

For a single-field index, direction is almost irrelevant — a B-tree walks either way. It becomes decisive for a compound sort, which an index serves only if the sort matches it exactly, or is its exact mirror.

db.rides.createIndex({ vehicle_type: 1, booking_value: -1 })

.sort({ vehicle_type:  1, booking_value: -1 })   // ✅ exact match
.sort({ vehicle_type: -1, booking_value:  1 })   // ✅ exact mirror
.sort({ vehicle_type:  1, booking_value:  1 })   // ❌ in-memory SORT
Why the ❌ hurts: in-memory sorts have a hard 100 MB limit. Past it the query does not slow down — it fails. A report that passed testing can break purely because the data grew.

Compound Indexes

The prefix rule, then ESR

Given { status: 1, vehicle_type: 1, booking_value: -1 }, the index serves any query using a left prefix of its fields:

Query filters onUsable?
status  ·  status + vehicle_type  ·  all three✅ Yes
vehicle_type alone  ·  booking_value alone❌ No — skips a leading field

The ESR rule — order compound fields Equality → Sort → Range

E exact matches first · S sort fields next · R range operators ($gt, $lt, $in over a span) last.

Why: equality narrows the B-tree to one contiguous block, inside which entries are still ordered by the next field — so the sort is free. A range selects a span, so anything after it is no longer in one sorted run and must be re-sorted in memory.

One well-ordered compound index often replaces three single-field ones: fewer indexes, less RAM, cheaper writes.
ESR · Worked on rides

"Completed Go Sedan rides over ₹500, newest first"

db.rides.find({
  status: "Completed",          // E — equality
  vehicle_type: "Go Sedan",     // E — equality
  booking_value: { $gt: 500 }   // R — range
}).sort({ date: -1 })           // S — sort

db.rides.createIndex({ status: 1, vehicle_type: 1, date: -1, booking_value: 1 })
//                     └── E ──┘  └──── E ─────┘  └─ S ─┘  └───── R ─────┘
Field orderWhat happensVerdict
status, vehicle_type, date, booking_valueEquality narrows the block; it is already ordered by date; range applied lastESR ✅
status, vehicle_type, booking_value, dateRange fans the scan, so date loses its order → an in-memory SORT appearsSlow
booking_value, status, vehicle_type, dateLeads with a range: the scan starts broad and stays broadWorst
Watch carefully: all three produce IXSCAN. "The index is being used" is not evidence the index is good. Only ESR gets docs-examined close to docs-returned.
Diagnosis

explain("executionStats") — four numbers

db.rides.find({ "route.pickup": "Connaught Place" })
        .explain("executionStats")
FieldMeaningWhat you want
stageCOLLSCAN / IXSCAN / FETCH / SORTIXSCAN. A SORT stage means an in-memory sort.
nReturnedDocuments actually returnedYour denominator — the useful work
totalDocsExaminedDocuments the engine had to readAs close to nReturned as possible
executionTimeMillisWall-clock timeThe headline — and the least trustworthy number

The metric is a ratio, not a time

totalDocsExamined ÷ nReturned. 1:1 is perfect. 10:1 is tolerable. 1,000:1 means the database did a thousand times more work than the answer needed — and it scales exactly that badly.

Prefer the ratio because it is hardware- and cache-independent. 12 ms on a warm laptop cache with a 1,000:1 ratio is an incident waiting for a cold start.
Before · After · Covered

Three tiers of query efficiency

❌ Scan — 13:1

stage: "COLLSCAN"
nReturned: 1139
totalDocsExamined: 15000
executionTimeMillis: 28

✅ Indexed — 1:1

// createIndex({"route.pickup":1})
stage: "IXSCAN"
nReturned: 1139
totalDocsExamined: 1139
executionTimeMillis: 3

🏆 Covered — 0 docs

stage: "PROJECTION_COVERED"
nReturned: 1763
totalDocsExamined: 0

A covered query is answered from the index alone — every filtered and returned field lives in the index, so the documents are never touched. Note that _id must be explicitly excluded:

db.rides.createIndex({ status: 1, vehicle_type: 1, booking_value: 1 })
db.rides.find(
  { status: "Completed", vehicle_type: "Go Sedan" },
  { _id: 0, vehicle_type: 1, booking_value: 1 }
)
Why engineer for it: indexes are far smaller than documents, so they are far likelier to be resident in RAM. Covered queries are the ideal shape for exactly the few-field, high-frequency reads dashboards make.
The Other Side of the Ledger

Indexes are not free — more is not better

1 · Every write pays

An insert writes the document plus one entry per index. Twelve indexes ≈ thirteen units of write work. The analytics team's indexes are paid for, permanently, by the booking ingest path.

2 · RAM is the whole game

Your working set is the data + indexes queries touch regularly. Fits in RAM → fast. Doesn't → disk reads, often 50× slower. Indexes compete with documents for that same cache.

3 · Unused indexes are pure cost

They still slow writes and still occupy RAM, while contributing nothing.

db.rides.aggregate([{ $indexStats: {} }])
// accesses.ops: 0 → drop candidate

Atlas Performance Advisor (Clusters → Performance Advisor) profiles real traffic and ranks index recommendations by expected impact, flagging unused and redundant ones too.

Use it, don't outsource judgement to it. It optimises each slow query in isolation — it knows nothing about your write volume or RAM budget. Accept a recommendation when you can explain it in ESR terms.
Half 2 · The Mental Model

A pipeline is a conveyor belt of stages

db.rides.aggregate([
  { $match: { status: "Completed" } },                  // 15,000 → 9,343
  { $group: { _id: "$vehicle_type",
              revenue: { $sum: "$booking_value" } } },  //  9,343 → 7
  { $sort:  { revenue: -1 } },                          //      7 → 7, ordered
  { $limit: 3 }                                         //      7 → 3
])
// → Premier Sedan ₹5,36,855 · Go Sedan ₹4,91,473 · Uber XL ₹4,31,927
SQLStageSQLStage
WHERE$matchORDER BY$sort
GROUP BY$group (key is always _id)LIMIT / OFFSET$limit / $skip
HAVING$match after $groupLEFT OUTER JOIN$lookup
SELECT col, expr$project / $addFieldsCOUNT(*)$count or { $sum: 1 }
Read a pipeline top to bottom as an English sentence. HAVING and WHERE are the same stage — only the position differs, and the position is the meaning.

The $avg trap: it skips missing fields rather than treating them as zero. So $avg: "$booking_value" over all 15,000 rides silently returns the average completed fare (₹235.73). Make the population explicit with $match.
The Golden Rule

$match and $limit as early as possible

❌ Late filter

db.rides.aggregate([
  { $group: { _id: "$vehicle_type",
      revenue: { $sum: "$booking_value" }}},
  { $match: { _id: "Go Sedan" } }
])
// groups all 15,000, discards most

✅ Early filter

db.rides.aggregate([
  { $match: { vehicle_type: "Go Sedan" } },
  { $group: { _id: "$vehicle_type",
      revenue: { $sum: "$booking_value" }}}
])
// groups 2,854 — a fifth of the work

Fewer documents for every later stage is merely arithmetic. The decisive reason is different: only a $match in the first position can use an index. Once any stage has transformed the stream, the documents are no longer the indexed documents on disk — every later $match is an in-memory filter over intermediate results.

Same logic for $sort: leading $sort → index-served. After $group → in-memory, against a hard 100 MB stage limit. $sort + $limit adjacent gets a special top-n optimisation.

Verify, don't assume: db.rides.aggregate([…]).explain("executionStats") — check the first stage. IXSCAN is the goal, COLLSCAN is the warning.

Questions 2 & 3

Dates are strings here — and that is the lesson

booked_at ("2024-03-14T18:22:07Z") and date ("2024-03-14") are strings, not BSON Dates. ISO strings sort lexicographically in date order, so substrings work — or convert properly.

// Q2 — revenue by month
db.rides.aggregate([
  { $match: { status: "Completed" } },
  { $group: { _id: { $substr: ["$date", 0, 7] },        // "2024-03"
              revenue: { $sum: "$booking_value" },
              rides:   { $sum: 1 } }},
  { $sort: { _id: 1 } }
])
// → Mar strongest ₹1,99,972 / 859 rides · Jun weakest ₹1,66,260
//   twelve months sum to the ₹22,02,449 of completed value

// Q3 — busiest hour of day
db.rides.aggregate([
  { $group: { _id: { $toInt: { $substr: ["$booked_at", 11, 2] } },
              bookings: { $sum: 1 } }},
  { $sort: { bookings: -1 } }, { $limit: 5 }
])

// The convert-first alternative:
{ $hour: { $dateFromString: { dateString: "$booked_at" } } }
{ $dateToString: { format: "%Y-%m",
    date: { $dateFromString: { dateString: "$booked_at" } } } }
Fix types at ingestion, not in every downstream pipeline. Converting 15,000 docs per query is cheap; converting 15 million is a daily tax — and strings support no range arithmetic, no time zones, no date-aware indexes.

Question 7 · Serving the Dashboard

Every KPI in one pass, then materialise it

db.rides.aggregate([{ $facet: {
  headline: [
    { $group: { _id: null,                       // null = one grand total
        total_bookings: { $sum: 1 },
        completed: { $sum: { $cond: [{ $eq: ["$status","Completed"] }, 1, 0] }},
        completed_value: { $sum: "$booking_value" },
        avg_distance_km: { $avg: "$ride_distance" } }}
  ],
  by_status:   [ { $group: { _id: "$status", n: { $sum: 1 } } },
                 { $sort: { n: -1 } } ],
  payment_mix: [ { $match: { payment_method: { $exists: true } } },
                 { $group: { _id: "$payment_method", n: { $sum: 1 } } } ],
  fare_bands:  [ { $match: { booking_value: { $exists: true } } },
                 { $bucket: { groupBy: "$booking_value",
                     boundaries: [0,100,250,500,1000], default: "1000+",
                     output: { rides: { $sum: 1 } } } } ]
}}])
// headline → 15,000 bookings · 9,343 completed · 62.29% · ₹22,02,449 · 10.87 km
// payment_mix → UPI 45.03% · Cash 25.31% · Wallet 11.79% · Credit 10.79% · Debit 7.08%

Then write the answer down once, so the dashboard reads results instead of raw data:

{ $out: "monthly_revenue" }                              // full rebuild, destructive
{ $merge: { into: "monthly_revenue", on: "_id",
            whenMatched: "replace", whenNotMatched: "insert" } }   // incremental, safe
Careful: a $facet sub-pipeline cannot use an index — the stream is already read. Put any index-eligible $match before the $facet, never only inside it.
Wrap-Up

Six things to carry forward

  1. An unindexed query is O(n). COLLSCAN reads everything; a B-tree IXSCAN is ~O(log n), so growth stops mattering.
  2. Compound field order is decided by ESR — Equality, Sort, Range — because a range selects a span, and nothing stays sorted behind a span.
  3. Judge a query by totalDocsExamined ÷ nReturned, not milliseconds. 1:1 is perfect; a covered query examines zero documents.
  4. Indexes are not free. Every write pays for every index and they compete with documents for RAM. Index the queries you run; drop what $indexStats shows unused.
  5. A pipeline is an ordered conveyor belt that maps almost one-to-one onto SQL: $match≈WHERE, $group≈GROUP BY, $sort≈ORDER BY, $project≈SELECT, $lookup≈LEFT JOIN.
  6. $match and $limit go first — later stages then do less work, and only a leading $match can use an index. Materialise with $out/$merge.
