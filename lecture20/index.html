Debrief · 5 Minutes

Ten teams just ran ten experiments

Same brief, ten independent attempts. This is the fastest learning available in the module — answer all three aloud.

1 · Which modelling decision did the most work?

Across ten projects, which single embed-or-reference call — or which key design — bought the most, and why?

2 · Which recommendation would you fund?

One budget line. Whose project gets it? Defend it in one sentence.

3 · What did everybody get wrong?

A failure that recurred across teams is a property of the brief, not of any one team. Name it out loud.

Peer forms in before the synthesis. Scores written from memory are flatter and less useful than scores written live.

Synthesis · The Asset

You will forget the syntax. Keep these five questions.

  1. What is the access pattern? Write down the three most frequent queries before naming a technology.
  2. What does a stale read cost? A rupee, or a slightly out-of-date view count?
  3. How fast does the schema change? Monthly favours documents; untouched-for-three-years favours relational.
  4. What is the realistic three-year volume? Honest growth, not ambitious growth.
  5. Who operates it at 3 a.m.? The best database for a team that cannot run it is the wrong database.

How to use it in a meeting

You do not need to know the technology being proposed. Ask questions 1 and 2 and watch what happens. If nobody can state the three most frequent queries, the decision is being made on fashion — send it back.

First stated in Lecture 11, before you had the experience to see why each question mattered.

Synthesis · The Central Trade

Every number is computed at one of two moments

Compute-on-read · MongoDB, L14

db.rides.aggregate([
  { $match: { booking_date:
      { $gte: ISODate("2024-01-01") } } },
  { $group: { _id: "$status",
              n: { $sum: 1 } } }
])

Work happens when someone asks. Any new question is free.

Compute-on-write · Redis, L18

INCR    rides:2024-06-14:total
INCR    rides:2024-06-14:status:completed
HINCRBY rides:2024-06-14:byhour 18 1

Work happens at ingest. Reads are O(1) — for questions you anticipated.

Not a MongoDB-vs-Redis question. The same trade recurs in warehouses, caches, materialised views, and every reporting system you will commission.
The Trade · In Full

What each choice costs you

Compute-on-readCompute-on-write
Work happensAt query time, every requestOnce, at ingest
Read latencyTens of ms to seconds, scaling with volumeSub-millisecond, flat regardless of history
A new questionFree — new pipeline, existing dataExpensive — new key, write-path code, backfill
Fixing bad dataFix documents; future queries correct themselvesFix documents and recompute every derived counter
StorageRaw data onlyRaw data plus every pre-computed aggregate
Right forExploration, ad-hoc analysis, monthly reportingLive dashboards, leaderboards, rate limits, counters
Fails whenQuery volume is high and latency must be flatQuestions change faster than you can ship code
The rule: compute on read until latency or volume makes it untenable — then move only the specific, stable, high-traffic questions.
The Hybrid

What real systems actually do

  1. Every ride is written to MongoDB as the system of record — complete, correctable, queryable on any field.
  2. The same write path increments a handful of Redis counters for the five numbers the live dashboard needs.
  3. The ops screen reads Redis and renders instantly.
  4. Analysts run pipelines against MongoDB for anything the counters do not cover — which is most new questions.
  5. A nightly job recomputes the counters from MongoDB, so drift is corrected within a day.

Step 5 is the one teams forget

Derived data drifts. With no scheduled path back to the source of truth, the dashboard slowly becomes confidently wrong — which is worse than being slow.

Pre-computing an aggregate is a commitment, not an optimisation. You are betting this question is still asked next year.
Synthesis · Polyglot

Several stores, each earning its place

WorkloadStoreThe property that decided it
Driver payouts and invoicesPostgreSQLMulti-row transactions; a stale read costs real money
Ride records and analyticsMongoDBShape varies by product line; ad-hoc queries on any field
Live surge and ops dashboardRedisSub-millisecond reads on a constantly refreshed page

Fraud ring detectionNeo4jMulti-hop traversal SQL cannot do at depth

The cost vendors omit

Every store is another thing to back up, monitor, patch, secure, capacity-plan and hire for — with consistency maintained by application code nobody enjoys writing. Two stores run well beat five run badly.

Correct when each store carries a genuinely different access pattern. Expensive when it is three databases doing one job because three teams had preferences.

The Frontier

Vector search moved into the document database

The most significant recent change in this space: Atlas Vector Search lets you store an embedding — a numeric array representing the meaning of text or an image — in an ordinary field alongside the rest of the document, index it, and query by semantic similarity rather than exact match.

Why it matters commercially

A retrieval-augmented system that recently needed a separate specialised vector database can now run on the store you already operate. It removes a system from the architecture.

The honest caveat

Dedicated vector databases remain faster at very large scale. Most organisations never reach that scale — so treat this as a strong default to evaluate, not a settled answer.

By question 5 of the framework, removing a system is usually worth more than any feature gained by adding one.
The Closing Argument

There is no best database

Only a best fit for a stated access pattern — and the manager's job is to force that pattern to be stated before the technology is chosen.

You will rarely write the migration. You will frequently be the person in the room who can insist the question is answered first.

  1. The five questions outlive the syntax. Apply them to technologies this course never mentioned.
  2. Every derived number is computed on read or on write. Move a question to write-time only once it is stable and expensive.
  3. Pre-computation is a commitment. Give derived data a scheduled path back to the source of truth, or it drifts into being confidently wrong.
  4. Polyglot persistence is normal and not free. Each store earns its place by carrying a different access pattern.
  5. Recommending the boring option when it fits is a senior move, not a timid one.
Ask "what are the three queries this system will run most often?" before anyone names a product — and notice how often nobody has written them down. That gap is where your value is. Thank you.
