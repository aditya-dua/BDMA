The Unit of Storage

This is a document

{
  _id: ObjectId("65f1a2c4e8b9d4a1c2f30142"),
  booking_id: "CNR3000142",
  booked_at: ISODate("2024-03-14T18:22:07Z"),
  status: "Completed",
  customer_id: "CID482910",
  vehicle_type: "Go Sedan",
  route:   { pickup: "Connaught Place", drop: "Aerocity" },
  booking_value: 412.50,
  ride_distance: 18.4,
  ratings: { driver: 4.6, customer: 4.8 },
  payment_method: "UPI"
}
Relationally this is three tables and two joins. Here it is one object, one read, in the exact shape the app displays.

No fare, no distance, no rating — because the ride never happened. Absence is the data. 4,756 of 15,000 documents have no booking_value.
Storage Format

You write JSON. Mongo stores BSON.

JSONBSON
FormTextBinary
Types6~20 — ObjectId, Date, Decimal128, Int32/64, Binary
Field orderUndefinedPreserved
Reading one fieldParse the whole stringLength-prefixed — skip straight to it
Why it costs money: a Double cannot hold ₹0.10 exactly. Sum a million fares and the ledger drifts. Money gets Decimal128; distances and ratings are fine as doubles.
Primary Key

Every document has an _id

ObjectId("65f1a2c4  e8b9d4a1c2  f30142")
          --------  ----------  ------
          4 bytes   5 bytes     3 bytes
          timestamp random      counter
          (seconds) per process per process
ComponentConsequence
TimestampSorting by _id ≈ sorting by creation time, free, no extra index
RandomTwenty app servers can generate IDs at once without colliding
CounterOne process can generate thousands per second, still unique
The throughput point: AUTO_INCREMENT needs a round trip to a single shared counter. An ObjectId needs no coordination at all.
Discipline

"Schemaless" is the most damaging word in NoSQL

The schema does not disappear. It moves from the database into your application code, your analysts' queries, and your dashboards.

What flexibility buys

Additive change with no downtime · heterogeneity that matches reality · fast iteration while the record shape is still unknown.

What it costs

payment_method vs paymentMethod — both writes succeed, reports quietly undercount. 412.5 vs "412.5" — range queries silently skip the strings.

A team that never writes a validator has not chosen flexibility. It has chosen neglect.
Re-Tightening

$jsonSchema — strictness you opt into

db.createCollection("rides", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["booking_id", "booked_at", "status", "route"],
    properties: {
      booking_id: { bsonType: "string", pattern: "^CNR[0-9]{7}$" },
      status: { enum: ["Completed", "Cancelled by Driver",
                       "Cancelled by Customer", "No Driver Found",
                       "Incomplete"] },
      booking_value: { bsonType: ["double","int"], minimum: 0 }
    } } },
  validationLevel: "moderate",
  validationAction: "error"
})
Note what is not required: booking_value. For 4,756 bookings its absence is correct. validationAction: "warn" first, "error" once the backlog is clean.
The Core Decision

Embed or reference?

Embed

{ booking_id: "CNR3000142",
  route: { pickup: "CP",
           drop: "Aerocity" },
  ratings: { driver: 4.6,
             customer: 4.8 } }

One query. No join. Atomic single-document write.

Reference

// rides
{ booking_id: "CNR3000142",
  customer_id: "CID482910" }

// customers
{ _id: "CID482910",
  name: "Priya Sharma" }

Two queries, or one $lookup in Lecture 14.

In SQL, normalisation decides this for you. In MongoDB you decide, every time — and this is where document models succeed or fail.
The Rule of Thumb

Five tests, one decision

TestEmbed when…Reference when…
AccessRead together with the parentRead on its own
SizeSmall and boundedLarge or unbounded
ChangeChanges with the parentChanges independently
SharingBelongs to one parentShared by many parents
CardinalityOne-to-one, one-to-fewOne-to-many, many-to-many
Compressed: embed what is read together, bounded, and changes together. When the tests disagree, access pattern wins — it is what users feel.
Applied

Our dataset, decided

RelationshipCallWhy
Booking → routeEmbedTwo fields, fixed at booking time, never read alone
Booking → ratingsEmbedTwo scalars, written once at trip end
Booking → cancellationEmbedSame business event, present only when relevant
Booking → customerReferenceOne customer, hundreds of rides; a phone change must not rewrite history
Customer → bookingsReferenceUnbounded — a commuter adds 500 a year, forever
Hybrid: embed a snapshot customer: { id, name } to skip the join. The name on an old receipt staying old is arguably correct, not a bug.
The Hard Limit

16 MB per document — and the trap it catches

// ANTI-PATTERN
{ _id: "CID482910",
  name: "Priya Sharma",
  bookings: [
    { booking_id: "CNR3000142", value: 412.50 },
    { booking_id: "CNR3000288", value: 180.00 },
    // ...one more every day, forever
  ] }

Four failures

Grows without bound · reading the name drags the whole history · every write relocates the document · a multikey index gets 5,000 entries per doc.

The fix

rides as its own collection with customer_id on each booking — exactly how our dataset is shaped.

Arrays are fine when bounded: tags, saved_addresses, fare_breakdown. If you cannot state the maximum with a straight face, reference.

)
Then open Compass → Schema tab: booking_value appears in only ~68% of documents. Not an error — the hook for Lecture 13.
Wrap-Up

Six things to carry forward

  1. A document is the unit of storage, and it nests. Collections have no fixed columns; fields can hold whole structures.
  2. You write JSON, Mongo stores BSON. Real types, preserved order, fast traversal. Money gets Decimal128.
  3. _id is mandatory; ObjectId is 12 bytes — timestamp + random + counter, so it is time-sortable and needs no coordination.
  4. Flexible schema defers the strictness decision — it does not delete it. $jsonSchema is how you take it back.
  5. Embed what is read together, bounded, and changes together. Reference what is large, unbounded, shared, or independent.
  6. 16 MB is a smoke alarm. The unbounded array is the fire it is listening for.
